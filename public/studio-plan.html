Content Studio

재료를 만들고, 가공하고, 바로 확인하는 웹 제작 작업공간

대화로 게임을 고치고, 편집기와 미리보기에서 바로 보고, 빌드하고, 링크로 출시한다.

01 / 문서

엔진과 편집기가 같은 파일

outputs/game/content/<scene>.studio.json 하나. 편집기는 아는 필드만 검증하고 나머지는 보존한다.

02 / 미리보기

게임 iframe + 오버레이

백엔드가 프로젝트 폴더를 서빙하고, 편집기는 그 위에 드래그 오버레이를 얹는다. 별도 렌더러가 없다.

03 / 출시

빌드 → 링크

outputs/game + assets + 엔진을 build/game/<version>/과 zip으로 묶고, /play/<slug>/ 또는 배포 명령으로 내보낸다.

원본 에셋→편집 문서→명령·검증→실행 미리보기→수정·저장↺편집 변경은 빌드 없이 즉시 반영

S5

한 파일 · 한 루프: 편집기 ↔ 엔진 ↔ 에이전트 ↔ 빌드

완료

장면 스키마를 엔진의 것으로 통일(sprite/rect/text, transform, props, logic 보존). content_preview.rs가 프로젝트 폴더를 서빙하고 편집기는 iframe 위 오버레이로 드래그한다. 엔진 계약: ?scene=, codeg:ready(hot), codeg:scene. 작업공간 감시 스트림으로 에이전트 편집을 즉시 반영. build_content_project가 build/game/<version>/과 zip을 만든다. 에이전트는 studio_* MCP 도구(목록·읽기·검증된 명령 적용·빌드)와 편집기의 '대화로 보내기'(장면·선택·런타임 오류)로 루프 안에 있다. 미리보기 서버가 HTML에 오류 보고 스크립트를 주입한다. 엔진은 프로젝트 밖의 관리형 런타임(codeg-engine three-web 0.3.0, Three.js r170 벤더링)이며 편집/플레이 모드·스크립트·트윈·입력을 제공한다. 빌드는 __codeg/를 실체화해 단독 실행된다. 출시: 빌드마다 Studio의 /play/<slug>/ 공개 링크(설정 없음, 버전이 바뀌어도 같은 주소) 또는 매니페스트 publish.command 실행 후 URL 기록. 편집기는 행동(props.script, 엔진이 알려 준 목록과 기본 설정), 그리기 속성(opacity·rotation·scale·flipX), 액션 단계(action.set/remove), 플레이 중 게임 변수와 다시 시작을 다룬다.

완료 기준 · 드래그 → 즉시 반영 → 자동 저장 → 에이전트가 파일 수정 → 편집기·iframe 갱신 → 빌드 → 출시 링크에서 로그인 없이 실행. 브라우저(codeg-server)에서 실제로 확인.
S6

제작 공정과 분야별 확장

예정

에셋 업로드(편집기 → assets/), 타임라인·애니메이션 클립, 타일맵, 오디오, 3D 지형·재질·내비게이션, 가공 작업·의존성·캐시·재생성, 0.2.x 프로젝트 이전 도구, publish 프리셋 UI, 매니페스트 agents 역할 반영.

완료 기준 · 원본 변경의 영향을 추적하고 필요한 산출물만 재생성한다.

이번 단계의 경계

  • 편집기는 프로젝트 폴더가 있어야 한다. ?path 없는 /studio는 안내만 보여 준다. 브라우저 초안·번들 내보내기는 제거됐다.
  • 실행 취소 이력은 현재 세션의 최대 50단계다. 파일 이력은 git이다.
  • 에이전트는 장면 파일을 직접 쓰거나 studio_* MCP 도구를 쓴다. 도구는 콘텐츠 프로젝트 폴더에서 연 세션에만 노출된다. 편집기의 선택 상태는 사용자가 '대화로 보내기'를 눌러야 에이전트에 전달된다.
  • 편집기가 편집하는 필드는 transform, props의 visible·asset·text·size·color·interactive·onClick·opacity·rotation·scale·flipX·script, logic.actions다. 액션 단계와 목록·객체형 스크립트 설정은 JSON으로 편집한다. 나머지 props와 logic은 보존만 한다.
  • 이미지 업로드 UI가 없다. 에셋은 assets/에 두고 장면 파일에 선언한다.
  • UI는 10개 언어 문자열이 있다. ko·en 외는 기계적 번역 수준이다.
  • 장면 검증기가 TypeScript(document.ts)와 Rust(studio_scene.rs) 두 벌이다. 규칙을 바꾸면 둘 다 고친다. Rust 쪽은 첫 프로토타입 포맷을 변환하지 않고 거부한다.
  • 미리보기는 게임 자체다. 관리형 엔진은 편집 모드에서 스크립트를 멈춘다. 모드를 모르는 엔진(0.2.x, 에이전트가 직접 쓴 엔진)은 오버레이 아래에서 계속 돌고, hot이 아니면 저장 뒤 iframe을 다시 불러온다.
  • 엔진은 2D 장면 런타임이다. 3D·물리·타일맵·오디오·파티클이 없다. 필요하면 스크립트에서 engine.THREE로 직접 그린다.
  • 0.2.x 프로젝트를 관리형 엔진으로 옮기는 자동 도구가 없다. index.html의 importmap과 src/main.js를 새 스캐폴드처럼 바꾸면 된다.
  • 빌드는 outputs/game·assets 복사 + 엔진(__codeg/) 실체화 + zip이다. engine.build가 있으면 먼저 실행하지만, 미리보기 전에 자동으로 돌리지는 않는다.
  • /play/<slug>/ 링크는 인증이 없고 Studio 서버만큼만 공개된다. 데스크톱에서는 이 기기와 LAN용이다. 외부 호스트는 publish.command가 부르는 CLI와 그 계정에 달려 있고, 프리셋 UI는 없다.
  • 행동 선택 목록과 액션 연산 안내는 실행 중인 엔진이 알려 준 것이다. 모드·목록을 알리지 않는 엔진(0.2.x, 직접 쓴 엔진)에서는 이름을 직접 입력해야 하고 게임 변수 패널이 나오지 않는다.

설계 결정

D01
게임을 첫 적용 분야로 삼는 범용 콘텐츠 제작 플랫폼

같은 재료와 편집 공정을 인터랙티브 웹·강의·시뮬레이션에서도 사용한다.

D02
첫 렌더러는 Three.js + React Three Fiber

현재 React 구조에 연결하며, 게임 동작과 분야별 기능은 별도 모듈로 추가한다.

D03
첫 제작 도구는 2D 장면 배치

원본 이미지 → 배치 → 클릭 동작 → 저장·다시 열기의 최소 전체 흐름을 빨리 검증한다.

D04
편집 문서와 런타임 객체 분리

렌더러 교체, 에이전트 편집, 데이터 검증, 실행 취소의 기준을 문서와 명령으로 유지한다.

D05
게임 전용이 아니라 세계관 정본에서 여러 결과물을 만드는 콘텐츠 프로젝트

웹툰·인스타툰·소설·영상 스토리보드가 같은 캐릭터와 설정을 공유해야 하며, 어떤 에이전트 CLI든 같은 폴더 규칙(AGENTS.md)을 읽게 하는 것이 다중 에이전트 협업의 최소 조건이다.

D06
편집기 문서 = 엔진 장면 파일, 미리보기 = 게임 iframe

두 포맷과 두 렌더러가 있으면 대화로 고친 게임이 편집기에 보이지 않는다. 에이전트가 자연스럽게 쓴 스키마를 정본으로 삼고 편집기가 거기 맞춘다.

D07
백엔드가 프로젝트 폴더를 HTTP로 서빙

module script·importmap·상대 fetch는 진짜 HTTP가 필요하다. 사용자가 npx serve를 띄우게 하지 않는다. iframe은 헤더를 못 실으므로 폴더 id가 자격이다.

D08
에이전트 도구는 파일에 쓰고, 편집기는 파일을 본다

MCP 도구가 프런트엔드 상태를 직접 건드리면 편집기가 닫혀 있을 때 동작하지 않고 두 번째 진실이 생긴다. 검증된 명령을 파일에 원자적으로 쓰면 기존 감시 스트림이 편집기·미리보기를 갱신한다.

D09
런타임 오류 보고는 엔진이 아니라 미리보기 서버가 주입

에이전트가 엔진을 통째로 다시 쓸 수 있고, 가장 중요한 오류는 아직 아무도 검토하지 않은 코드에서 난다. 엔진 계약에 의존하지 않는다.

D10
엔진은 프로젝트에 복사하지 않고 Studio가 제공한다

프로젝트마다 엔진 사본이 있으면 에이전트가 고치는 순간 갈라지고, 편집기가 이해하는 부분이 줄어든다. 예약 경로 __codeg/를 미리보기는 가상으로, 빌드는 실체로 제공하면 프로젝트는 장면과 스크립트만 갖고 출시물은 자족적이다.

D11
편집 모드와 플레이 모드를 엔진이 구분

스크립트가 노드를 움직이면 문서 기준의 선택 상자와 화면이 어긋난다. 편집 중에는 문서 그대로, 플레이에서는 문서에서 새로 시작하는 것이 유니티·고도의 편집/실행 구분과 같다.

D12
출시는 Studio가 직접 서빙하는 링크가 기본, 외부 호스트는 프로젝트의 명령

호스트마다 연동을 만들면 계정·토큰을 Studio가 떠안는다. 빌드가 자족적인 정적 폴더이므로 서버 배포에서는 그 폴더를 공개 경로로 서빙하는 것만으로 출시가 되고, 그 밖의 호스트는 engine.build와 같은 방식(매니페스트의 셸 명령, 환경 변수로 경로 전달)이면 어떤 CLI든 쓸 수 있다.

D13
편집기의 엔진 개념은 엔진이 알려 준 것에서 나온다

행동·연산 목록을 편집기에 하드코딩하면 엔진과 어긋나고 프로젝트가 등록한 스크립트가 보이지 않는다. 엔진이 codeg:ready로 등록된 이름과 내장 스크립트의 기본 설정을 알리면 편집기는 그것으로 선택 목록과 입력란을 만들고, 저장은 기존 props·명령 경로를 그대로 쓴다.
